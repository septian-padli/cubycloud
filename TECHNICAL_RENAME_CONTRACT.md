# Technical Rename Contract: CubyCloud → CubyCrate

**T1 audit only.** Baseline: `origin/main` at `6905416d5279318f572a832c54984ad1ea42e318`. Target display spelling: `CubyCrate`; target new machine spelling: `cubycrate`. Repository: `septian-padli/cubycloud`. This document is a proposed execution contract for owner review, not permission to run T2–T8, delete development data, rename repositories, publish packages, or deploy.

## Scope and decision boundary

The owner states that the application is pre-alpha without real users and chooses a **Clean Break** before the next alpha. This supersedes the phase-one *technical-identifier preservation* boundary in `BRAND.md:151-180` and `REBRANDING_PLAN.md:81-96,168-170` **for future owner-approved technical work only**. It does not supersede the approved brand spelling, visual system, historical provenance, data-preservation requirement, or independent release approvals. Existing code and docs remain unchanged in T1. Clean Break means the next technical release need not read old cookies, old browser keys, or old runtime names indefinitely; it does **not** mean existing development databases, keys, local files, S3 objects, or volumes may be discarded. No automatic dual-read shim is assumed. First inventory actual data, obtain a disposition for each instance, and use an explicit offline copy/restore or migration where retention is required. Historical release notes and migration records retain the name used at the time.

### T2–T6 owner decision (2026-11-06)

The owner approves **Clean Break + Fresh Start** for this integration PR. This decision supersedes T1's retained-development-data prerequisite, offline-copy migration gates, and compatibility proposals for T2–T6 only. No direct upgrade from `v0.0.1-alpha.1` is supported. ## Data preservation and reset boundary

No deployment, volume, bucket, browser profile, or local development directory was modified or inspected for contents in T1. Therefore **actual data ownership and disposable status are unknown**. The owner's statement that no real users exist does not establish that all development data is disposable. A DB-only admin download (`internal/modules/admin/repository.go:48-57`, `handler.go:143-176`) is **not** a full backup: it excludes local blobs, external S3 objects and key material. The `docs/backup-restore.md:31-67` cold archive method describes the broader scope; its restore example at `:71-102` destroys target content and must **never** be used as a T1 check. For retained data, plan cold stop/checkpoint, record WAL status, export all state to an immutable backup outside affected volumes, restore to a separate destination and test before changing the live instance. For approved resets, constrain deletion to an enumerated copy/instance; keep the original snapshot until owner accepts post-cutover validation. Rename of master-key **variable** must carry same key bytes; do not rotate encrypted material as an incidental rename.

Rollback after any data-format or namespace write is **not** merely changing image tag: old binaries may not read rewritten keys or DB state. Stop writes, restore the pre-cutover **DB and blobs and secrets together** on isolated mounts, restore previous Compose/image and proxy config, then verify `/health`, authenticated login and representative local/S3 downloads. Keep the old GHCR digest and GitHub release/tag record; do not delete old volumes/buckets or re-enable orphan deletion until retention window and owner sign-off. For GitHub/Worker cutover separately record last good repo URLs, build SHA and Worker deployment ID before editing external settings; a Git revert alone does not restore deployed state.
